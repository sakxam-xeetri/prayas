1. Why JSON? The Control & State Backbone of Prayas AI
Protocol Rationale & Engineering

In Project Prayas AI (Node 05), communication is split into two specialized planes: a JSON-based Control Plane operating over MQTT (or WebSocket) and a Binary UDP Media Plane streaming encrypted Opus audio. Here is the deep technical explanation of why JSON was chosen for control and state management:

1. Self-Describing & Extensible Schema
Embedded systems evolve rapidly. JSON allows introducing new capabilities (such as mcp tool calling, emotion tokens, or camera frame configurations) without breaking existing ESP32 C-firmware parsers. Unknown fields are safely ignored by cJSON.
2. Native Cloud LLM & API Interoperability
LLMs (DeepSeek, Qwen-Max, OpenAI GPT-4o) natively output text and JSON function calls. Passing JSON directly between the Cloud Orchestrator and ESP32 avoids costly binary serialization/deserialization layers in server microservices.
3. Asynchronous State Synchronization
Voice interactions are event-driven: handshakes (hello), recording mode toggles (listen), emergency user interruptions (abort), and execution callbacks (mcp). JSON provides clear event types ("type": "llm") for state machines.
4. Decoupled Control vs Media Stream
Raw audio requires low latency UDP without TCP head-of-line blocking. Control messaging requires structural clarity. Separating JSON control from Opus audio UDP ensures large state packets never stutter 60ms audio playback.

          3. MQTT + UDP Hybrid Communication Protocol Lifecycle
        

        Dual Channel Protocol
      


      

        To guarantee real-time voice response without audio stuttering, Xiaozhi AI separates signaling and data into two distinct channels:
      


      

        

          
          Protocol Lifecycle & Handshake Flow
        


        

          

            
STEP 01 • MQTT CONNECT

            
MQTT Control Link

            
Device establishes secure MQTT connection to server (KeepAlive: 240s, ClientId, Auth credentials).

          


          

            
STEP 02 • HELLO EXCHANGE

            
Audio Channel Request

            
Device sends "type": "hello" JSON with audio params (Opus, 16kHz, 60ms). Server returns UDP port, AES key & nonce.

          


          

            
STEP 03 • UDP AES-CTR INIT

            
UDP Audio Channel

            
Device initializes 128-bit AES-CTR encryption context using negotiated udp.key and udp.nonce.

          


          

            
STEP 04 • OPUS STREAMING

            
Real-Time Audio Loop

            
Bi-directional compressed Opus audio packets stream over UDP with sequence & timestamp protection.

          

        

      


      

        Encrypted UDP Opus Audio Packet Binary Specification
      


      
      

        

          Binary Packet Header • Encrypted UDP Opus Audio Packet
          
        

        
|  Type (1B)  |  Flags (1B)  | Payload Len (2B) | SSRC (4B) | Timestamp (4B) | Sequence (4B) | Encrypted Payload (N Bytes) |
|   0x01      |    0x00      |     Network      |  Sync Src |   Network Byte  | Monotonic Seq  |    AES-CTR Encrypted Opus   |

Field Definitions:
- Type (1 Byte): Fixed 0x01 for Audio Stream Data
- Flags (1 Byte): Reserved flag bits (0x00 default)
- Payload Length (2 Bytes): Network byte order (Big-Endian) length of encrypted Opus audio frame
- SSRC (4 Bytes): Synchronization Source Identifier for multi-device stream identification
- Timestamp (4 Bytes): Monotonically increasing audio frame timestamp (Network Byte Order)
- Sequence Number (4 Bytes): Monotonically increasing sequence counter for replay protection & packet ordering
- Encrypted Payload: 128-bit AES-CTR encrypted Opus audio frame using key & nonce negotiated via MQTT JSON Hello

          7. Model Context Protocol (MCP) & Smart IoT Control
        

        AI-to-Hardware Control
      


      

        The Model Context Protocol (MCP) enables the Xiaozhi AI assistant to convert spoken human intents into concrete hardware actions across all Prayas V1 robot nodes (e.g. driving motors, setting servo angles, reading telemetry sensors).
      


      

        

          JSON Protocol • MCP Async Tool Call Executed by ESP32
          
        

        
// Server -> ESP32: Invoking registered hardware function tool
{
  "type": "mcp",
  "payload": {
    "action": "call_tool",
    "tool_name": "set_servo_angle",
    "arguments": {
      "node_id": "node-02",
      "servo_channel": 1,
      "angle_degrees": 90
    }
  }
}

// ESP32 -> Server: Execution Result Callback
{
  "type": "mcp",
  "payload": {
    "status": "success",
    "tool_name": "set_servo_angle",
    "result": { "status": "OK", "current_angle": 90 }
  }
}

      

    


    
    

      

        

          
          8. DIY Step-by-Step Compilation & Build Guide
        

        ESP-IDF Setup
      


      

        Follow these steps to configure the ESP-IDF build environment and flash the Xiaozhi firmware to your ESP32-S3 development board.
      


      

        

          Terminal Commands • ESP-IDF Compilation & Flashing Workflow
          
        

        
# 1. Clone Xiaozhi ESP32 repository
git clone --recursive https://github.com/xiaozhi-esp32/xiaozhi-esp32.git
cd xiaozhi-esp32

# 2. Set ESP32-S3 target architecture
idf.py set-target esp32s3

# 3. Configure Wake Word engine & Board settings
idf.py menuconfig
# Navigate: Component config -> ESP Speech Recognition -> Select Wake Word ("你好小智")
# Navigate: Xiaozhi Assistant -> Language Settings -> Select Default Locale ("zh-CN" / "en-US")

# 4. Build firmware project
idf.py build

# 5. Flash to ESP32-S3 board and open monitor terminal
idf.py -p COM3 flash monitor

      


      

        

          
          Important Configuration Note for N8R2 Boards (8MB Flash / 2MB PSRAM):
        

        

          If using N8R2 instead of N16R8, open menuconfig and change PSRAM working mode from OCTAL to QUAD, set Flash size to 8MB, and point the custom partition table to partitions_8M.csv before compiling.
